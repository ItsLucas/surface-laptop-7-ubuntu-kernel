# 7.3 Wi-Fi 睡眠恢复回归（2026-09-19）

## 现象与定位

设备为 Surface Laptop 7 13.8 英寸 X1E / Romulus13，Wi-Fi 为 WCN7850 hw2.0。
Ubuntu 源包 `7.3.0-5.5` 基于 `v7.3-rc3`，本机内核为 `7.3.0-5-sl7.8.1`。
升级后 deep 睡眠能进入，但唤醒时 ath12k 等待 restart completion 超时，Wi-Fi 不可用。
等待期间用户空间尚未解冻，会表现为开盖后长时间黑屏。

关键改动为 [544d85de4dc2：Send HELLO message on endpoint register](https://github.com/torvalds/linux/commit/544d85de4dc22c01badfd8cefa59829ce35c4858)。
它解决某些被动 WLAN 固件与主机互相等待的问题：在 endpoint 注册时主动发 HELLO，
同时删除 nameservice 收到 HELLO 后的回复。

ath12k 系统睡眠通过 `mhi_power_down_keep_dev()` 保留 MHI/QRTR endpoint。
恢复时固件重启、通道重新准备，但 endpoint 不重新注册。
新的主动 HELLO 因而不会再次发送，旧的回复也被移除。
实测 trace 显示 MHI 和 QRTR 的 resume_early 均成功，收到固件 HELLO 后却没有 WLAN 服务登记。

## 对照结果

三个实验均使用同版固件 `WLAN.HMT.1.1.c7-00108`，构建日期 `2026-03-06`。
模块签名、Secure Boot 和其他 SL7 补丁保持不变。

| 条件 | 结果 |
|---|---|
| 7.3 原始 QRTR，默认 PCIe D3cold 策略 | Wi-Fi 恢复超时，用户空间恢复被延迟约 24 秒 |
| 7.3 原始 QRTR，仅禁止 Wi-Fi D3cold | Wi-Fi 控制器不再停链/重建，但同样恢复超时；不能作为修复 |
| 7.3 回退上述 QRTR 提交，恢复默认 D3cold 策略 | 一次手动 deep 睡眠恢复成功，Wi-Fi 自动连接，failed_resume=0，用户确认网络可用 |

成功实验的原始 trace：

```text
143.139998  qcom_mhi_qrtr resume_early begin
143.141741  qcom_mhi_qrtr resume_early end, err=0
143.143192  QRTR HELLO received from WLAN node
143.146030  QRTR NEW_SERVER received
143.146034  WLAN QMI service 0x45 registered
145.964733  ath12k resume begin
145.964735  ath12k resume end, err=0
```

失败对照中，ath12k resume 回调等待约 20.286 秒后返回 `-110`；
MHI 上电到用户空间恢复的总等待约 24 秒。
回退后 HELLO 到服务登记约 2.842 毫秒，进入 ath12k resume 时固件重启已完成。
8471 条 trace 事件全部保留，无 buffer overrun。触摸设备的 ready 状态恢复且 SPI 错误计数为 0。

这些证据支持将**本次 WLAN 服务发现失败**定位为该 QRTR 改动引入的回归。
它不证明固件、PCIe 或显示恢复的所有问题都已解决：成功实验仍有 PCIe L2 entry timeout，
较早对坏状态 Wi-Fi 热重绑触发的 MHI Oops 也未经过修复验证。不要用自动 unbind/bind 作为恢复策略。

## 携带补丁与未来更新

`0006-revert-qrtr-register-only-hello.patch` 完整回退该单一提交，恢复前一版握手实现。
这是一项面向本机内核的临时回退，保留了旧实现的适用范围和限制；
不声称解决上游原提交针对的所有被动远端启动场景。
后续应在完整的上游恢复修复可用时替换或删除，并重新验证冷启动与多轮睡眠。

0006 列在 `patches/series-if-needed`，在五个必需硬件补丁后检查：

1. 正向 `--dry-run --fuzz=0` 成功，才实际应用回退。
2. 若失败，仅对明确列入该清单的补丁做反向 **dry-run**，验证所有修改后的代码块已存在；
   例如未受影响的 Ubuntu 7.2。验证成功则记录 `not-needed`，不会实际反向应用或改变源码。
3. 两种已知状态都不匹配，或只有部分修改，立即失败并走现有 GitHub 通知流程。

这个判断按源代码状态执行，不把 7.3 写死；将来上游采用不同修复时会要求人工审阅，
不会仅因文件名相同或补丁失败就自动认定已修复。
`BUILD.json` 的 `patch_application` 记录每个补丁的实际决定，输入补丁与清单均参与 recipe 指纹。

公开仓库只记录通用补丁和脱敏的诊断摘要，不上传本机原始网络日志、固件、校准或密钥。
新 CI 产物仍为 signed candidate；这里的一次实机验证针对上述内核加独立 QRTR 模块，
完整新构建安装后仍需常规硬件验收，不能直接晋升为长期验证过的 stable。
